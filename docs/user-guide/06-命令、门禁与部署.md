# 06 命令、门禁与部署

## 命令表

从 `package.json` 抄的，一条不落：

| 命令 | 干什么 |
|---|---|
| `npm install` | 装依赖。需要 Node 22.19 或更高 |
| `npm run build:data` | 把 `data/raw/` 固化成 `src/data/*.json` |
| `npm run verify` | 数据门禁：输入指纹、白名单账目、出处自洽、今译覆盖率 |
| `npm run dev` | 先 `build:data`，再起 Vite 开发服务器 |
| `npm test` | Vitest 单元与组件测试，**不带覆盖率**，日常开发用这条 |
| `npm run test:coverage` | 同一批用例带覆盖率跑，并按 `vite.config.ts` 里的阈值判定。`npm run build` 走的是这一条 |
| `npm run test:e2e` | Playwright 端到端 + axe 可访问性扫描。要先 `npm run build`；首次先 `npx playwright install chromium` |
| `npm run audit:design` | 设计体检，5 视口 × 深浅主题 × 4 页面共 40 组。要先 `npm run build` |
| `npm run build` | 完整门禁链，见下一节 |
| `npm run build:single` | 先跑完 `npm run build`，再做单文件构建（`SINGLE=1`）到 `dist-single/`，并对该产物再跑一次体积检查 |
| `npm run single` | 只做单文件构建与体积检查，用于已经构建过的场合（CI 在 `build` 之后跑这条） |
| `npm run serve` | 用 `python3 -m http.server` 静态伺服 `dist/`，端口 5178 |
| `npm run typecheck` / `npm run lint` / `npm run format` / `npm run format:check` | 类型检查、ESLint、把代码写成 prettier 形态、只判定不改动的形态检查（后者是 `build` 的第一环） |
| `npm run check` | `build`、`test:e2e`、`audit:design` 三项连跑。交代码前跑这条 |

## `npm run build` 的八道关卡

```
format:check → build:data → verify → tsc --noEmit → eslint . → vitest run --coverage → vite build → size-check
```

任何一环失败，构建就失败。CI 与本地跑的是同一条链，所以"本地绿、CI 红"通常只可能是环境差异（Node 版本、压缩实现、字体）。

各关把的是什么：

| 关卡 | 断言 |
|---|---|
| `prettier --check .` | 代码、脚本、CSS、YAML 与 JS/JSON 配置必须已是 prettier 形态（单引号、保留分号、行宽 120、尾逗号、箭头参数必带括号）。Markdown 文档、`index.html`、`ANDROID.html`、`data/raw/`、`src/data/*.json` 与三类测试产物目录不参与格式化，见 `.prettierignore`——文档表格保持紧凑写法，否则改一个单元格会得到整张表的 diff |
| `verify.mjs` | 原始数据指纹、白名单账目（`L0_size = L0_seed + L0_added`）、候选出处自洽、单字名覆盖、今译覆盖率（唯一原句数等于释义条数、一句一译）、五部标注只落在 L0 字上、性别表规模、候选编号前缀碰撞统计与 `meta.id_prefix_stats` 对账。种子版与扩表版走不同断言分支 |
| `tsc --noEmit` | `strict` + `noUncheckedIndexedAccess` + `noUnusedLocals`。后者要求没有没用的局部变量与导入；前者要求按下标取值时先确认它存在（`CHARS`、`GLOSS`、`RADICAL` 这类 `Record<string, …>` 取出来是 `T \| undefined`）。生产代码的修法是一处判空、走已有的兜底分支，**不允许借判空改变判定**，也不新增 `!`、`as`、`@ts-ignore`。测试里"这条数据必须存在"的前提改用 `src/testing.ts` 的 `at` / `one`，取不到就抛"用例前提不成立" |
| `eslint .` | 覆盖 `src/`、`scripts/`、`tests/` 与 `public/sw.js`（后者按 Service Worker 全局检查，它没有单元测试，原本只能靠浏览器运行暴露错误）。`dist/`、`dist-single/` 与测试产物目录不检查 |
| `vitest run --coverage` | 覆盖率阈值，任一条低于即失败。口径见下面两节 |
| `size-check.mjs` | 两条判定都按 gzip 计、都进退出码：非 HTML 资源合计 ≤ 448 KiB（0.16.0 起，此前 400 KiB）；HTML 自身按产物形态取预算（站点版量页面壳 400 KiB，没放宽过；单文件版量整个产物 512 KiB，此前 450 KiB）。同时打印原文件大小与所用的压缩实现 |

还有一条在 CI 里、不在 `build` 里：`npm audit --audit-level=high`，只拦 high 与 critical，moderate 只报不拦（dev 依赖的 moderate 常常只能等上游）。

## 体积预算：先看数字，再看谁先撞线

当前实测（gzip level 9，版本 0.17.0，本机 zlib 1.3.1 口径）：

| 产物 | 原文件 | gzip（CI 口径） | gzip（本机口径） | 预算 |
|---|---:|---:|---:|---:|
| 站点 `dist/` 非 HTML 资源合计 | — | 待该版 CI 记录 | 432,077 B（421.9 KiB） | 458,752 B |
| 站点 `dist/index.html` 页面壳 | 2,922 B | 待该版 CI 记录 | 1,299 B | 409,600 B |
| 单文件 `dist-single/index.html` | 1,658,527 B（1.58 MiB） | 待该版 CI 记录 | 454,250 B（443.6 KiB） | 524,288 B |

**gzip 的结果跟压缩实现有关。** GitHub Actions 上的官方 Node 自带 zlib-ng，同一份单文件产物压出 414,892 B，比本机系统 zlib 的 409,115 B 多 5,777 B（1.4%）。门禁取较大的一侧作准。这条不是纸上原则：0.2.0 第一次把这条判定接进 CI 时就是被这个差值撞挂的——当时产物 413,537 B，400 KiB 预算在 CI 口径下过不去（超 3,937 B），本机口径下刚好通过，本机绿、CI 红。据此单文件产物单列 450 KiB 预算：它把本体与数据全装进一个 HTML，首屏的 400 KiB 对它过窄。

**先撞线的一直是站点那条，不是单文件那条。** 按本机口径现在两条余量是：站点 458,752 − 431,467 = 27,285 B（5.9%），单文件 524,288 − 453,652 = 70,636 B（13.5%）。语料增量同时加在两侧产物上，所以限制仍来自余量小的那条。这两条上限在 0.16.0 放宽过（站点 400→448 KiB、单文件 450→512 KiB，页面壳 400 KiB 未动），放宽的理由写在 `DESIGN.md` 6.1 与 `README.md` 的体积那一节：用户决定按 web 端体验定预算，不再以旧安卓机与 PWA 的首屏下载量为硬约束。

扩表能加多少条名字也算过：从 `src/data/candidates.json` 里删掉池子最后 300 条双名，重量三个数据文件的 gzip 差值，得到**每条双名 73.3 B gzip**（CI 口径；记录本身 57.8 B + 只有它用到的今译 21.3 B；本机 zlib 下 72.4 B）。按它换算，站点那条约 **280 条双名**即撞线，单文件那条约 626 条。**这条换算基于 0.3.1 的产物形状**：0.9.0 把原句与篇名收成共享表之后，同一做法实测每条 19.9 B gzip，能装的条数按余量重算，见 `README.md` 的那两段边际成本。扩表前按站点那一行算幅度；新增典籍原文、字表与读音条目不在这 73.3 B 之内，只会让上限更早到。

单文件那条在 0.16.0 之前一直是 450 KiB（460,800 B），当时的理由是：要放宽的是一条永不发布的产物的天花板，真正的约束仍在站点那条。0.16.0 用户把两条一起放宽（448 与 512 KiB），旧理由留在这里备查。`dist-single/` 只用于体积核对，不发布。

## 测试的三层

| 层 | 命令 | 当前规模 |
|---|---|---|
| 单元与组件 | `npm test` / `npm run test:coverage` | 15 个文件、347 个用例（含下面那 18 条门禁用例） |
| 端到端 | `npm run test:e2e` | 每个浏览器 51 个用例（关键路径 40 项 + 390×844 与 320×640 两档视口各 5 项）；本机跑 Chromium 与 Firefox 两档，合计 101 项跑过＋1 项跳过 |，含 axe（WCAG 2 A/AA）扫描与 target-size 规则，深浅主题均覆盖 |
| 设计体检 | `npm run audit:design` | 46 个组合：320×640、390×844、768×900、1024×900、1440×1000 × 浅色与深色 × 四个页面共 40 组，另有手机三档视口 × 深浅主题的 6 组「多出处展开」（0.17.0 加：点开「另有 N 处出处」并全部展开后再量一次） |

**端到端跑哪几个浏览器（0.18.0 起）。** 本机两档：Chromium 与 Firefox，`playwright.config.ts` 里就是这两个 project，CI 的 e2e job 也只跑这两档——它们红了拦发布。WebKit（也就是 Safari 那一系）本机跑不起来：系统缺 libevent-2.1、libavif16、libmanette、libgav1、libhidapi-hidraw、libbacktrace 六个库，逐个 `apt-get download` 解到浏览器自己的 `sys/lib` 之后进程起得来，页面握手仍 30 秒超时。所以它在 CI 里单列一个 `continue-on-error: true` 的哨兵档：红了不拦发布，但 CI 页上看得见。0.18.0 那次 CI 里它绿过一回（51 项跑过、强制颜色那条跳过）；连着两次绿就并进上面那个拦发布的 job。想本机试三档：`PLAYWRIGHT_WEBKIT=1 npx playwright test`。之所以值得接进来，是因为发布口径里有 iOS 与安卓的 PWA，而 Safari 的 `<details>/<summary>` 样式、粘顶页头、`focus()` 之后滚不滚、隐私模式下 `localStorage` 直接抛，都和 Chromium 不是一套行为。
| 门禁自身 | `tests/gates/`（随 `npm test` 一起跑，纯 Node） | 18 条用例，测 `verify.mjs` 与 `size-check.mjs` 的失败路径 |

设计体检检查横向溢出、触控目标尺寸、文字对比度、方块字行长、页头是否遮挡首屏卡片、页头高度。**硬违规五条**（有则退出码 1）：横向溢出超过 1 px、触控目标小于 24 px（复选框按整条 label 算）、对比度低于 WCAG 要求（大字 3:1、正文 4.5:1）、页头压住首屏第一张卡片、主题切换控件在窄视口不可见。"单行方块字超过 42 字"与"窄视口目标小于 44 px 但不少于 24 px"只作为报告段落输出，不影响退出码。`--verbose` 列逐条结果，`--json` 输出 `design-audit.json`。脚本在端口 5180 无响应时会自行启动 `vite preview`，所以可以直接在 `npm run build` 之后运行。CI 构建日志需要额外权限才能读，所以脚本把违规写成 `::error::` 注解。

## 覆盖率口径（为什么有些文件是 0%）

阈值：行 91%、语句 90%、函数 90%、分支 83%。实测 93.76 / 87.08 / 95.41 / 95.96，各留 4.1～5.4 个百分点——要能拦住"覆盖掉了"，也不该因一次小重构就红。阈值只按收口时的实测定一次，不追着实数拧两次。

分母只算 `src/` 下自撰的可执行代码。以下**不计入分母**，这不是漏测而是口径：

- `src/data/` —— `build:data` 写出的语料 JSON，不是代码。
- 测试文件本身。
- `src/styles.css` —— CSS 不是可执行代码，v8 执行不到它，算进去只会让数字失真。
- `scripts/*.mjs` —— 门禁脚本是被 spawn 出去的子进程，v8 插桩抓不到；它们由 `tests/gates/` 从行为上测。

剩下的差值也写在明面上：`main.tsx` 0%（它只做挂载与 Service Worker 注册，由端到端在真浏览器里覆盖，单元口径看不见）；`App.tsx` 语句 89.3% / 分支 78.78%（余下的是同一批回调在自选页与收藏页上的重复入口）；`Compose.tsx` 分支 93.78%、`NameCard.tsx` 分支 86.26%（界面上走不到的 `continue` 守卫与取窗防御支）；`data.ts` 77.6%（语料自检的失败分支，语料本身是全绿的）。

**覆盖率高不等于用例有效。** 这批断言另做了一轮变异抽查：在临时副本里逐条改坏生产代码 10 处，看指定用例是否变红，10 处全部被咬住；抽查还揪出六处"不会红的断言"并改写成能变的断言，明细在 `CHANGELOG.md` 的"用例强度复核"一段。

## CI 与发布

| 工作流 | 文件 | 内容 |
|---|---|---|
| CI | `.github/workflows/ci.yml` | 构建矩阵 Node 22 与 24；`npm ci` → `npm audit --audit-level=high` → `npm run build` → `npm run single`。另有三个 job：e2e（Node 22 + Chromium 与 Firefox，跑 `npm run build`、`npx playwright test --project=chromium --project=firefox`、`audit:design`）、设计体检在那一档里、WebKit 哨兵档（`continue-on-error: true`，只跑 `--project=webkit`）。同一分支的并发运行只保留最新一次，**但 main 上的 CI 不取消**——每次推 main 都会另外触发 Pages 发布，取消主干 CI 会让那个提交留下"已发布、CI 没有结论"的状态。单个 job 20 分钟超时（这个键必须写在 job 一级，写在 workflow 顶层整份文件会被判非法）。工作流权限只给 `contents: read` |
| 发布 | `.github/workflows/deploy-pages.yml` | 推 main 即构建并上传 Pages 产物，构建复用本地同一套门禁（`npm run build`）。也可在 Actions 页手动触发。`concurrency` 只保留最新一次部署 |
| 依赖更新 | `.github/dependabot.yml` | 每周六 09:00（Asia/Shanghai）开 PR：npm 只提 minor 与 patch（major 留给人工决定），标题前缀 `fix(deps)`，开放 PR 上限 5；GitHub Actions 依赖前缀 `chore(ci)`。带 major 的安全更新照旧提 PR（`applies-to: version-updates` 只挡版本更新），否则"公告有补丁但机器人不许提"会和门禁里的 `npm audit` 互相卡住 |

首次配置一个新仓库：

1. 创建**公开**仓库并推送代码（免费账户只能从公开仓库发布 Pages）。
2. 仓库 Settings → Pages → Build and deployment，把 Source 设为 **GitHub Actions**。
3. 推送后访问 `https://<用户名>.github.io/naming-app/`。

本项目不含密钥与个人数据。

## 什么时候升版本号

版本号只有一个来源：`package.json` 的 `version`，形态（`x.y.z`，可带预发布后缀）在构建期校验，不对就就地停构建。语料口径由 `src/data/meta.json` 的 `corpus_sha` 表示。

| 情形 | 版本号 |
|---|---|
| 语料口径变（`corpus_sha` 变） | 升 minor（这条自 0.1.0 起还没触发过） |
| 新增用户可见功能或改变输入口径 | 升 minor |
| 只修缺陷、只收紧门禁或只补许可与类型强度，但产物字节变 | 升 patch |
| 只动测试、门禁配置与文档，产物逐字节不变 | 不升，记在 `CHANGELOG.md` 的"未发版"段 |

升版本时四件事一起做：改 `package.json` 的 `version`；在 `CHANGELOG.md` 顶上新写一段条目（语料是否变化、用户可见影响、门禁与口径、实测数字）；**在该提交上打注释标签 `vX.Y.Z`**；推送后核对 CI 与 Deploy 两个 run 的结论并在版本索引表补一行。

标签的锚点规则：打在"`package.json` 的 `version` 第一次取该值的提交"。要回到某一版最后一次进过线上的状态，用索引表里"该版最后一次提交"那一列。读 Actions 历史时有两条事实要知道：一次推送只按 head 建 run（中间提交不单独产生 run），以及索引表里挂着两条红的 CI run，都不是那一版的门禁跑红（原因写在 `CHANGELOG.md` 的版本索引后面）。
