# 04 数据与语料

这一篇讲数据从哪来、怎么流进应用、许可怎么分。想核对"这个出处是真的吗"的人，这一篇最有用。

## 一条流水线

```
data/raw/          上游语料、字表、派生输入、指纹清单、许可全文
   │  npm run build:data   （scripts/build-data.mjs）
   ▼
src/data/*.json    构建产物：候选、字表、今译、白名单、风险表、meta
   │  vite build
   ▼
dist/              站点产物（发布）      dist-single/  单文件产物（不发布）
```

`src/data/` 下的文件**全部是产物，不要手工编辑**。改了会被下一次 `npm run build:data` 覆盖。要改数据，改 `data/raw/` 里的输入，然后重跑构建。

## 七部典籍与它们的来源

| 输入文件 | 上游 | 许可 | 进包吗 |
|---|---|---|---|
| `shijing.json` `chuci.json` `lunyu.json` `shuimo.json` `song300.json` | chinese-poetry/chinese-poetry | MIT | 不进包，只发布清洗后的句读候选 |
| `daofa.json` | 本仓库手工录入的 22 条句读行（《老子》王弼本系通行本、《周易》经与十翼、《清静经》），逐行核对归属 | 古籍本文属公共领域 | 不进包，这 22 行以 `candidates.json` 的 `line` 字段发布 |
| `yuefu.json` | 郭茂倩（宋）《乐府诗集》二十篇（汉乐府 13、北朝乐府 5、南朝乐府 2），文本自中文维基文库各卷页抄录，并与《四库全书》本交叉校字 | 原集公共领域；维基文库整理本 CC BY-SA 4.0 | 不进包，只发布清洗后的候选与原句引文 |

两份看起来省事、实际被拒的路线值得记下来：

- **庄子、列子、黄帝阴符经没有整本收录。** 那个"道家数据集"里的庄子文本实为《现代庄子》白话改写本（"思泉"出自"他那心思如喷泉"、"天城"出自"那家伙被押送到深山老林去服刑"），列子与阴符经夹带现代注家语。以整本取词等于引用现代整理本。门禁还反向断言：锐可、智慧、圣智、鼎金、坤天等 33 个只在整本语料里才会出现的名字必须在池外，语料被换成整本抓取文本时门禁直接失败。
- **白话过滤器不可用。** 试过按现代虚词密度逐段剔除：阈值 0.14 时在已知纯文言的语料上只保留 76.4% 的段；要把文言保留率提到 94%，就只能剔除 7.6% 的白话。这个指标区分不了文言与文学性白话，所以文言 / 白话的判定只能在整本层面做。这也是"道法"只手工录入 22 行的原因。

乐府的取舍也写在 `data/raw/LICENSES.md`：不收《箜篌引》（维基文库该条正文只有唐代李贺拟作，汉古辞仅见于解题引文，引文不属于正文，收进来会导致出处标注错误）；《上山采蘼芜》按《玉台新咏》录入并以此标注出处；《木兰诗》只取其一（卷二十五收两首，其二不取，两首都收会在同一篇内引入两套异文）。

| `line_gloss.tsv` | **本项目自撰**，1,140 行 | 本项目原创 | 出处今译 |
| `l0-verdicts.txt` | 本项目人工判定 | — | 白名单里人工保留的字，单独校验文本指纹，不在 `SHA256SUMS` 里 |

`scripts/derive-dict.mjs` 是一次性派生工具，默认从 `UP_DIR`（`/tmp/opencode`）读上游词典与姓名语料，裁出上面三份精简输入。这三份派生文件已经登记进指纹清单，日常构建不再需要上游原件。

**一条纪律**：不引入任何他人的现代译文。古典诗文本身属公共领域，许可风险来自现代整理本的注释与译文。水墨唐诗的 `prologue` 是现代赏析短文，不参与取词也不发布。参考项目 gushi_namer 的代码与语料 JSON 都不复用（该仓库没有任何 LICENSE 文件，默认版权保留），只读懂机制、自己重写。

## 指纹与语料指纹

`data/raw/SHA256SUMS` 记录每份输入的 SHA-256，`npm run verify` 在构建期逐份校验。改动任何原始数据都必须同步更新指纹：

```bash
$ cd data/raw
$ ls | grep -v -e SHA256SUMS -e LICENSES.md -e licenses -e l0-verdicts.txt | xargs sha256sum > SHA256SUMS
$ npm run build
```

构建时 `build-data.mjs` 把这份清单的 SHA-256 前 12 位写进 `src/data/meta.json` 的 `corpus_sha`，页脚显示"语料指纹 …（语料清单变化即变）"。当前值是 `b30924ef5d04`。用户能从页脚判断自己拿到的是哪一份语料——这是"这个出处是不是真的"这件事上，应用给出的第一个可核对凭证。

`licenses/` 目录与 `LICENSES.md` 属于许可元数据，不算语料输入，指纹不覆盖它们，否则改一句说明就会被误判为语料漂移。

## 扩充白名单的正确做法

白名单不是一次定死的，但扩它要走指定流程：

```bash
$ node scripts/l0-unlock.mjs      # 生成边际增量待审表（每个字能带来多少条新名字）
# 人工逐字判定，把"保留"的字写进 data/raw/l0-verdicts.txt
$ npm run build
```

扩表之后门禁切换到**下界断言**模式：已有的候选不允许消失，账目断言 `L0_size = L0_seed + L0_added` 也要对上。种子版（没有 `l0-verdicts.txt`）走的是另一条断言分支。

改白名单规则还需要同步诊断脚本那条链路：`measure-funnel`、`measure-l0-curve`、`measure-gap-ladder` 现在统一通过 `scripts/l0-keep.mjs` 的 `buildL0()` 并入保留字，与 `build-data.mjs` 同口径，否则它们会误报口径漂移。

## 增加典籍要同时改的地方

加一本书不是扔一个 JSON 进去就完事，需要同时更新：`data/raw/` 语料与 `SHA256SUMS`、`build-data.mjs` 的取词参数、`src/engine/types.ts` 的 `BOOK_ORDER`、`verify.mjs` 的语料规模与出处断言、界面文案里的典籍计数。乐府并入那次就是这么做的，而且门禁钉死了它的规模（429 段、2,134 字、按书新增 22 条），全池只允许两条出处改判，其它改动直接失败。

## 许可怎么分层

| 范围 | 许可 |
|---|---|
| 本仓库自撰的代码与文档 | MIT，全文见仓库根 `LICENSE` |
| `data/raw/` 的上游语料、字表、派生输入 | 各自上游许可，本仓库不重新授权 |
| 构建期用到的第三方库 | 上游许可（React、Vite、TypeScript、Tailwind 等均为 MIT；pinyin-pro MIT；构建期用、运行时不打包，省 141 KB gzip） |
| 上游许可全文副本 | 随包发布在 `data/raw/licenses/`，离线单文件版同样满足归属要求 |

数据与文档的逐项上游、许可与用途以仓库 `data/raw/LICENSES.md` 为准，这一篇只是它的导读。
