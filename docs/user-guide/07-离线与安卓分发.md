# 07 离线与安卓分发

这个应用的定位是"运行时零网络请求"，所以离线不是附加功能，是它的本行。安卓方向目前只有方案没有代码，这一篇末尾写清楚了现状。

## 三种离线形态

| 形态 | 怎么得到 | 需要什么 | 更新方式 |
|---|---|---|---|
| 站点 + Service Worker（PWA） | 直接访问线上地址，可装到主屏幕 | 首次联网一次 | 部署即更新 |
| 单文件 HTML | `npm run build:single` 出 `dist-single/index.html` | 一个文件，双击打开 | 重新构建、重新发文件 |
| 安卓应用 | 需要按下面的方案实施 | Android 工具链或托管站点 | 看选哪条路 |

## PWA 的离线机制

应用壳在 `public/`：`manifest.webmanifest`、`icon.svg`、`icon-192.png`、`icon-512.png`、`sw.js`。注册集中在 `src/lib/pwa.ts` 的 `usePwa()`，只在 http(s) 下注册（`file:` 协议下不注册，免得单文件版双击打开时去抢浏览器缓存），对外暴露 `offline`、`updateReady`、`applyUpdate`。

`sw.js` 的 fetch 处理分两路：

- **导航请求走 network-first**。部署新版后刷新即取到新 `index.html`，不会被旧缓存顶住。网络失败时退回缓存里的这一条，再没有就退回缓存的 `index.html`。
- **带哈希的静态资源走 cache-first**。未命中时走网络并回填当前这一版的缓存。

资源既没缓存又连不上网络时，回一个 504 的纯文本小响应，**不退回 `index.html`**。原先的做法等于把一段 HTML 当作 `.js` / `.css` 交给浏览器，用户看到的是"脚本语法错误"这种看不懂的表现。这个 504 也不写进缓存。

### 缓存名是算出来的，不是写死的

旧版本把缓存名写成 `naming-app-v5`：改一次代码要手改一次，漏改时新产物被写进旧缓存，`activate` 又把"名字不匹配"的缓存删掉，用户看到的是旧内容。现在的推导顺序：

1. `fetch('./index.html', { cache: 'no-store' })`。不能用缓存里的那一份，它可能属于旧版本。
2. 取其中的 `assets/*.js`、`assets/*.css` 文件名排序后哈希，得到 `naming-app-<hash>`。产物内容变了文件名就变，缓存名跟着变，旧缓存由 `activate` 删除。
3. 没有分包产物（单文件版）时退回 `index.html` 里 meta 的版本号，得到 `naming-app-0.3.1` 这样的名字。
4. 连 `index.html` 都取不到（离线安装）时退回注册参数 `?v=`；都没有则 `naming-app-unreleased`。

同一个 worker 实例只解析一次；`activate` 只删除带 `naming-app-` 前缀且与当前名字不同的缓存，不碰别人的缓存。端到端里有一条用例直接从浏览器读缓存，验证名字形态以及应用壳确实写进了这个缓存。

### 版本号只有一个来源

`package.json` 的 `version` 是唯一出处，`vite.config.ts` 读它并校验形态，不对就停构建。三个出口都由它注入：

| 出口 | 注入方式 | 用途 |
|---|---|---|
| JS 常量 `APP_VERSION` | `define` | 页脚"应用版本 …"；`usePwa()` 的注册参数 |
| `index.html` 的 `<meta name="app-version">` | `transformIndexHtml` 替换占位符（`define` 不改 HTML） | 单文件版离线打开时可核对版本，也是缓存名的第二回退 |
| Service Worker 注册参数 `sw.js?v=` | `pwa.ts` 拼 URL | 版本变化时浏览器更及时去取新的 worker |

与版本并列的另一个对外口径是**语料指纹**：`data/raw/SHA256SUMS` 的 SHA-256 前 12 位写进 `src/data/meta.json` 的 `corpus_sha`，页脚显示"语料指纹 …（语料清单变化即变）"。版本号和语料指纹合起来回答"这次用的是哪份语料"。

`public/manifest.webmanifest` 里没有 `version` 成员，不是漏了：应用 manifest 规范已移除该成员，浏览器不读它，安装与"有新版本"提示走 Service Worker 这条路。

### "有新版本可用"什么时候提示

要求同时存在 `waiting` worker **和**旧版控制权。首次访问只有 `waiting` 时不提示——那时候没有"旧版本"可换。点"刷新"时向等待中的 worker 发 `SKIP_WAITING`，`sw.js` 在 `message` 监听里处理。注册失败只静默收口，不把 rejection 漏到全局。

## 安卓：三条路怎么选

**仓库当前不包含任何 Android 工程代码**，下面全是方案说明（口径来自仓库 `ANDROID.md`，更新于 2026-10-26）。

| 方案 | 改动量 | 更新方式 | 离线 | 原生能力 | 前置条件 |
|---|---|---|---|---|---|
| PWA 直接安装 | 无 | 部署即更新 | 首次联网后可离线 | 弱（Web Share API） | HTTPS 托管 |
| TWA（Bubblewrap） | 低 | 网页部署后应用自动更新，无需重新发版 | 首次需要联网 | 弱 | HTTPS 托管、Digital Asset Links、打包与签名 |
| Capacitor | 中 | 改代码后 `cap sync` 重新打包发版 | 安装后即可离线 | 强（系统分享、文件系统） | Android 工具链（JDK、Gradle、Android Studio）与签名 |

选择依据：

- 只需要在安卓上以应用形式使用 → 先发 PWA，零改动。
- 需要网页改动即时生效、不重新发版 → TWA，代价是首次联网与对托管站点的依赖。
- 需要完全离线、商店分发、原生分享 → Capacitor（`ANDROID.md` 推荐的实施路径）。
- 跨平台原生重写（React Native、Jetpack Compose）不在范围内：canvas 分享卡、二维码生成、词典装配都要重新实现，还要长期维护两套代码。

两条渠道可以并行：同一份 `dist` 既作为 PWA 提供免安装与即时更新，也打进 Capacitor 用于商店分发与完全离线。

## Capacitor 实施要点

架构上增加一层 `src/platform/`，网页与安卓共用界面与引擎，只在底层分流平台相关调用。需要适配的调用点只有五处：

| 位置 | 网页行为 | 安卓行为 | 需要的适配 |
|---|---|---|---|
| `src/lib/pwa.ts` 的 `usePwa` | 注册 Service Worker | 跳过注册 | `isNative()` 分支 |
| `src/App.tsx` 的 `doShare` | 二维码指向 `location.origin` | 用系统分享面板发图，二维码指向线上正式地址 | `shareImage()`、`canonicalUrl()` |
| `src/App.tsx` 的 `doCopyLink` | 复制当前地址 | 复制线上正式地址 | `canonicalUrl()` |
| `src/lib/share.ts` 的 `downloadBlob` | `<a download>` | `@capacitor/filesystem` 写文档目录，再 `@capacitor/share` 分享 | `saveFile()` |
| `src/App.tsx` 的 `doPrint` | `window.print()` | WebView 打印能力受限，改为导出名单长图并分享 | 复用 `shareImage()` |

平台层接口（建议放在 `src/platform/index.ts`）：`isNative()`、`canonicalUrl()`、`saveFile(blob, filename)`、`shareImage(blob, title)`、`registerSW()`。`src/engine/`、`src/store/`、`src/styles.css` 与大部分 `src/ui/` 不需要改动。

构建步骤：

```bash
$ npm i -D @capacitor/cli
$ npm i @capacitor/core @capacitor/android @capacitor/share @capacitor/filesystem
$ npx cap init "取名" com.example.naming --web-dir=dist
$ npx cap add android
$ npx @capacitor/assets generate     # 由 public/icon-512.png 生成整套图标与启动页
```

`capacitor.config.ts` 关键项：`appId`（例如 `com.example.naming`，**上架后不可更改**）、`appName`（取名）、`webDir`（`dist`）、`backgroundColor` 与 `android.allowMixedContent`（混合内容保持关闭）。

`package.json` 建议加的脚本：

```json
{
  "android:sync": "npm run build && npx cap sync android",
  "android:apk": "cd android && ./gradlew assembleDebug",
  "android:aab": "cd android && ./gradlew bundleRelease"
}
```

签名：生成 keystore 并妥善备份（**丢了就无法更新已上架应用**），参数写进 `android/keystore.properties`，在 `android/app/build.gradle` 中引用。上架产物是 `.aab`。

发布与迭代：签名 → 出 `.aab` → Play 控制台内部测试轨道 → 封闭测试 → 正式发布。应用不收集数据，"Data safety" 填报为不收集，但仍需提供一个隐私政策链接。每次发版递增 `versionCode`、更新 `versionName`。Capacitor 没有内置热更新，纯 JavaScript 改动也要重新打包上传；要即时生效就走 PWA 渠道，或者引入 `@capawesome/capacitor-live-update`。

## 还没定的事

这五条来自 `ANDROID.md`，动手之前先拍板：

1. 是否上架 Google Play（上架需要开发者账号、签名 keystore、隐私政策）。
2. 迭代优先级是即时更新（倾向 PWA / TWA）还是完全离线与原生体验（倾向 Capacitor）。
3. 是否已有稳定的 HTTPS 托管域名（PWA 与 TWA 需要，Capacitor 不需要）。
4. 是否需要原生分享与保存图片到相册（需要则选 Capacitor）。
5. `appId` 的最终取值。
